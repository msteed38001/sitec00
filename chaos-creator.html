The Levels of Chaos

The Chaos Engine is a Python-based data corruption generator. It applies escalating levels of stress to your test pipelines. (Levels 1 through 4 generate the mess. Level 5 documents how AI creates the mess. Level 4 is the final encoding torture test.)

Level 1: Typos & Casing

Simulates human error. Randomly changes casing, transposes characters, and adds trailing spaces to names and codes. If your join keys aren't trimmed or normalized, this will catch it.

Level 2: Phonetic Shifts

Uses Soundex and phonetic swapping to generate "looks right, sounds wrong" data. Tests how fuzzy-matching algorithms handle duplicate vendors or misspelled customer names.

Level 3: Invisible Characters

Injects Zero-Width Spaces (ZWSP), homoglyphs, and mojibake. To the human eye, the data looks perfectly clean. To your database, the join key doesn't match, and the invoice fails silently.

Level 4: BOM Torture Files

Generates files in UTF-8, UTF-16LE, UTF-16BE, and UTF-32. It forces your parser to deal with the Byte Order Mark (BOM). If your tool strips the BOM "for convenience," it breaks downstream consumers that expect it.

Level 5: The AI Reference Library. AI is not a corruption generator. It is a clean-data generator. But it has its own chaos: it invents sources, fabricates details, and silently substitutes NULLs. Level 5 documents exactly how AI behaves so you know what to ignore and what to verify.

The Pandas Problem

I don't use Pandas. And neither should you - at least not for mission-critical data ingestion.

Pandas is famous for silently "fixing" data. The latest versions strip BOMs because they consider it a "pesky remnant." But that BOM was telling your downstream system what encoding to expect. When Pandas removes it, it silently corrupts the contract.

The Chaos Engine proves exactly where and how Pandas fails. It finds the silent data loss, the NaN conversions, and the encoding mismatches before they hit your production database.

Running the Chaos Engine

The engine is driven by TOML profiles and command-line flags, so you can target the exact type of corruption your pipeline needs to be tested against.

Here is how I run it against a sample CRM dataset:

# Test for phonetic mismatches (Soundex)
python src/main.py run --profile profiles_crm.toml --variant soundex

# Test for human typos and casing errors
python src/main.py run --profile profiles_crm.toml --variant typos

# Test for invisible characters (ZWSP, etc.)
python src/main.py run --profile profiles_crm.toml --variant hidden

# Generate a clean baseline for comparison
python src/main.py run --profile profiles_crm.toml --variant clean_baseline

# Run full corruption (all levels combined)
python src/main.py run --profile profiles.toml --variant full_corruption

The Ground Truth Ledger

Corrupting data is easy. Knowing exactly what you corrupted is the hard part.

When the engine generates a corrupted dataset, it simultaneously writes a "Ground Truth" YAML file. This acts as a ledger. It records the original value, the corrupted value, and the specific mutation applied.

This allows you to test your pipeline against the corrupted file, and then use the YAML file to audit exactly where and why your pipeline failed.
